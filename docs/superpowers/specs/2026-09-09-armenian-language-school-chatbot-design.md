# Armenian Language School Chatbot Design

## Goal
Build a repository-backed Armenian language assistant that is embedded directly into a dedicated page of the existing WordPress site. WordPress owns only the frontend embed. Supabase owns the database and API. The API must search trusted database knowledge first and use generative AI only when the database cannot answer confidently.

## Deployment shape
- No custom WordPress plugin.
- No separate public frontend website.
- Create a normal WordPress page such as `Armenian Language Assistant`.
- Paste the generated self-contained embed block into an Elementor HTML widget or Gutenberg Custom HTML block.
- The embed calls one Supabase Edge Function over HTTPS.
- The Edge Function is the only component allowed to call OpenAI or write to protected Supabase tables.
- The repository stores database migrations, Edge Functions, frontend source, tests, and the generated WordPress embed.

## Request flow
1. Student enters an English or Armenian question in WordPress.
2. Browser sends `message`, `clientId`, and optional `sessionId` to the public `armenian-chat` Edge Function.
3. Edge Function validates the request, checks allowed origins, and consumes a rate-limit slot.
4. Edge Function performs a database-only lexical search first: exact normalized question, aliases, trigram similarity, and simple full-text/keyword scoring.
5. A strong approved lexical match is returned directly without an OpenAI call.
6. If lexical search is inconclusive, the Edge Function generates a query embedding and performs vector similarity against approved knowledge.
7. A strong vector match is returned directly from the database.
8. Medium-confidence matches are supplied to the LLM as trusted context so it can explain or synthesize without replacing the database as the source of truth.
9. With no useful context, the LLM may answer from general knowledge under a strict Western Armenian prompt and must state uncertainty when appropriate.
10. Messages and answer provenance are logged. AI fallback answers are recorded for human review and are never automatically promoted to trusted knowledge.

## Search policy
- Stage A: exact/alias/lexical search in Postgres only.
- Stage B: semantic search only after Stage A fails to produce a strong result.
- Stage C: direct DB answer when semantic confidence is high.
- Stage D: RAG answer when semantic confidence is medium.
- Stage E: controlled AI fallback when no relevant approved knowledge exists.
- Only rows with `is_approved = true` can be returned or used as trusted context.

## Embeddings
- Default embedding model: `text-embedding-3-small`.
- Default dimensions: 512 to reduce vector storage and index size while using the v3 shortening capability.
- Embedding model name is configurable through an Edge Function secret.
- Knowledge rows store their embedding in `extensions.vector(512)`.
- Knowledge embeddings are generated by a separate protected/admin Edge Function or explicit maintenance command, not by public database writes.

## Chat model
- Default model: `gpt-5.6-luna`.
- Model name is configurable through `OPENAI_CHAT_MODEL`.
- Responses API is used with low verbosity and reasoning effort set to `none` for this focused language-assistant workload.
- `store: false` is used for application calls; conversation history is managed in Supabase.

## Database model
### `chatbot_knowledge`
Trusted source material.
- `id uuid primary key`
- `question text not null`
- `normalized_question text not null`
- `answer text not null`
- `category text`
- `language text default 'Western Armenian'`
- `keywords text[] default '{}'`
- `source text`
- `is_approved boolean default false`
- `embedding extensions.vector(512)`
- `created_at`, `updated_at`

### `chatbot_question_aliases`
Alternate question phrasings.
- `id uuid primary key`
- `knowledge_id uuid references chatbot_knowledge on delete cascade`
- `alias text not null`
- `normalized_alias text not null`
- timestamps

### `chatbot_sessions`
Anonymous session metadata.
- `id uuid primary key`
- `client_hash text not null`
- `created_at`, `last_seen_at`

### `chatbot_messages`
Conversation history and provenance.
- `id uuid primary key`
- `session_id uuid references chatbot_sessions`
- `role text check ('user','assistant')`
- `content text`
- `source text check ('user','database','ai_with_context','ai_fallback')`
- `knowledge_id uuid nullable`
- `created_at`

### `chatbot_ai_answers`
AI-produced answers awaiting review.
- `id uuid primary key`
- `normalized_question text not null`
- `question text not null`
- `answer text not null`
- `context_ids uuid[] default '{}'`
- `status text check ('pending','approved','rejected') default 'pending'`
- `times_asked integer default 1`
- timestamps

### `chatbot_rate_limits`
Hashed anonymous traffic buckets.
- `key text primary key`
- `window_started_at timestamptz`
- `request_count integer`
- `updated_at`

## SQL/RPC responsibilities
- Normalize searchable text consistently.
- Maintain normalized question/alias columns through triggers.
- `search_chatbot_knowledge_lexical(query, limit)` returns approved scored matches.
- `match_chatbot_knowledge(embedding, threshold, limit)` returns approved vector matches.
- `consume_chatbot_rate_limit(key, max_requests, window_seconds)` atomically enforces a request bucket.
- RLS is enabled on all chatbot tables with no public mutation policies. The Edge Function uses a server-side secret key.

## Security
- OpenAI key exists only in Supabase Edge Function secrets.
- Supabase secret/service-role key never appears in WordPress or browser code.
- Public chat function uses `verify_jwt = false` because learners are anonymous.
- CORS is restricted to configured WordPress origins in production.
- Request body and message lengths are validated.
- Client ID plus request IP are hashed with a server-only salt before rate-limit/session storage.
- Database answers come only from approved knowledge.
- AI answers never automatically become trusted knowledge.

## WordPress embed
- One self-contained generated HTML block with scoped CSS and JavaScript.
- Configurable `apiUrl`, assistant title, intro, and optional colors at the top of the block.
- No Supabase secret or OpenAI key.
- Generates/persists an anonymous browser client ID.
- Stores returned session ID in localStorage.
- Responsive chat UI, loading state, error/retry state, accessible send button, and keyboard toggle.
- Armenian keyboard inserts characters at the current cursor position.
- Designed for one dedicated WordPress page but safe to reuse later.

## Repository layout
- `supabase/migrations/` database schema and search functions.
- `supabase/functions/armenian-chat/` public chat API.
- `supabase/functions/embed-knowledge/` protected helper for embedding approved knowledge rows.
- `frontend/` source CSS/JS/template.
- `embed/wordpress-embed.html` generated block pasted into WordPress.
- `scripts/build-embed.mjs` creates the self-contained embed.
- `tests/` Node tests for frontend helpers and pure chat policy functions.
- `docs/setup.md` beginner-friendly setup instructions.

## Testing
- Test-first coverage for message validation, response-source decisions, OpenAI response parsing, allowed-origin handling, keyboard insertion, and frontend payload shaping.
- Build script must deterministically generate the WordPress embed.
- SQL migration receives static sanity checks and is compatible with Supabase Postgres extensions used by the project.
- TypeScript Edge Function receives compiler/static checks where the local environment permits.
- Final repository must contain no real secrets or project IDs.

## First-release exclusions
- WordPress plugin.
- User accounts, subscriptions, and billing.
- WordPress admin CRUD for the knowledge base.
- Automatic AI-answer approval.
- TunApp UI integration.
- A second standalone public frontend site.
